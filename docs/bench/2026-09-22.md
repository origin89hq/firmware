# Bench session, 2026-09-22

Board A rev A, ST-LINK V2-1 `0671FF565357657287183750`, equipment
disconnected, no wire on the module. Controller image unchanged from
`a52acc8` (102 464 bytes); comms images built from `ce81fbe` on
`david/m3-rollback-bootloader` (#68), clean source, version
`0.0.0+gce81fbe7`. Module flashed only through the controller's download
bridge (`o89-dev`, esptool 5.4.0). Module boot text read through the same
bridge (`just dev-comms-listen`); controller log over RTT (`just
attach-controller`). No analyser.

## The bootloader `espflash` ships has no rollback (F-088)

Established before the board was touched. `espflash` 4.5.0's bundled
`esp32c6-bootloader.bin` (22 592 bytes, SHA-256
`402c2c64…201cd`) is ESP-IDF `v5.5.1-838-gd66ebb86d2e`. Its
build manifest in the `espflash` repository sets only
`CONFIG_ESPTOOLPY_FLASHSIZE_64MB`; ESP-IDF's `Kconfig.app_rollback`
defaults `BOOTLOADER_APP_ROLLBACK_ENABLE` to `n`; and every rollback path in
`bootloader_utility.c` logs at debug level, which is compiled out, so the
binary's strings could not decide it. Every bench flash before this
session wrote `New` into the `otadata` of a module whose bootloader ignored
the field: a crashing update would have kept its slot for good.

`firmwares/o89-comms/bootloader/build.sh` builds ESP-IDF v5.5.1's
bootloader in `espressif/idf:v5.5.1` with the option on. Two builds gave
the same 22 560 bytes, SHA-256
`e32bd9a3577c0eba7d05e5e97dd8d6f474df7349d1a834fdea9410332d4e8ec3`, and
the script refuses a build whose resolved `sdkconfig` lacks the option.

## 1. The whole flash, by the knock

`just --yes dev-flash-comms-whole --entry knock`: the module, running the
`a52acc8` image, answered the knock; esptool erased `0x0`–`0x2bfff` and
wrote 178 432 bytes at `0x0` in 24.9 s, hash verified; the module reset
normally. The module now holds the rollback bootloader, the table and the
ordinary image as its factory image.

## 2. The slot route against the new bootloader (F-088)

`just dev-flash-comms`: before writing, the tool read 32 768 bytes at `0x0`
(17.2 s) and 4 096 at `0x8000`, compared the first against the merged
image, then blanked the `otadata`, wrote 112 896 bytes into `ota_0` at
`0x210000` and named the slot. The next boot's text:

```text
I (23) boot: ESP-IDF v5.5.1 2nd stage bootloader
I (140) boot: Loaded app from partition at offset 0x210000
```

## 3. #1's acceptance test, first half: the image that crashes at once

`just dev-flash-comms-crash`: 83 232 bytes into `ota_0` as `New`, the
module reset normally. The next reset of the module by the controller
showed the bootloader's decision:

```text
rst:0x1 (POWERON),boot:0x8 (SPI_FAST_FLASH_BOOT)
I (90) boot: Defaulting to factory image
I (144) boot: Loaded app from partition at offset 0x10000
```

The bootloader had marked the slot pending on its first boot, the image
panicked before its window and reset, and at that reset the bootloader
marked the slot aborted and fell back to the factory image. On the
controller's log the link came up on `0.0.0+gce81fbe7` with a ROM-text
count of 2 123 against the 1 060 to 1 094 of an ordinary boot: the extra
boots of the crash loop, counted (F-031). Nothing was touched by hand.

## 4. Recovery through the window, no wire

`just dev-flash-comms`: the knock was answered by the factory image
(`download (Bench) by Knock`, `the module is entering download mode`), the
bootloader region read back and accepted, 112 896 bytes written into
`ota_0`, and the next boot loaded `0x210000` again.

## 5. #1's acceptance test, second half: the window omitted (F-089)

`just dev-flash-comms-no-window`: 106 768 bytes into `ota_0` as `New`. The
image ran and linked, the controller reporting
`fw: "0.0.0-nw+gce81fbe7"`, ROM text 1 067, and could not confirm its slot:
the crate's `WindowRan` is made only by the window, and this image has no
window module at all. `just dev-flash-comms` then knocked: the knock's
reset had the bootloader mark the slot aborted and boot the factory image,
whose window answered (a windowless image answers no knock, so the answer
is the factory image's), and 112 896 bytes went into `ota_0`. The next boot
loaded `0x210000`.

## State left on the bench

The module runs the ordinary `ce81fbe` image from `ota_0` under the
rollback bootloader, with the same build as its factory image. The
controller is unchanged, at boot count 130 throughout, uptime continuous
across the session. Controller log attachments during the session were
closed by a timeout in probe-rs's default blocking mode; the final
attachment used `--rtt-channel-mode no-block-skip` and saw the link up,
and the mailbox answered after it.

## Limits

The `otadata` bytes were not read back between steps; the bootloader's
own log lines and the partition it loaded are the evidence of each state.
The controller log was not attached during the flashes, since the probe
carries the bridge; the knock's answer in step 5 is inferred from the
flash succeeding and the windowless image having nothing that answers.
The crash image's panic is a software reset; a hang ending in the RTC
watchdog's reset takes the same path through the bootloader and was not
run separately.

The three comms images were rebuilt from the same clean source after the
session for their hashes; the bench flashed the builds of the moment,
which the same toolchain produced from the same commit.

## 6. The resynchroniser against the pair pulled a thousand times (F-086)

Later the same day, on `david/m3-cut-bench`, comms images built from `3d2e074`
with uncommitted changes (`0.0.0-dirty+g3d2e0746`), the controller's frames
bench image from the same tree. The cut bench: the frames bench with the
sender pulling the pair on the wire itself, a thousand pulls of three
frames each, the first cut short of its delimiter at a point that sweeps
the frame from its first byte to its last, the second running into the
fragment, the third to arrive whole. The host replays the same plan through
KM43's reader and expects 1 000 arrived, 1 000 refused, none abandoned.

**First run, four frames a batch.** With the sender's batches of four, a
pull straddled the gap between batches every fourth pull, and the reader
met the other shape of the fault there: the fragment abandoned across the
quiet, or merged into a heartbeat that went out first.

```text
230.033 frames since the link came up: 1390 read, 835 refused, 165 abandoned, 0 overruns, 0 other line errors
230.033 frames of the run: 1173 arrived, highest numbered 3000, 1827 missing, link up 1 time(s)
```

Refused and abandoned sum to the thousand pulls; the arrivals are the
thousand third frames, the 165 second frames read whole after an abandon,
and 8 second frames read whole after the fragment merged into one of the
link's own frames. No pull cost more than the frame the rule allows, but the
run measured two shapes at once, so the sender was changed to send a pull
a batch.

**The clean run.** Controller reset by the probe so counters and sender
started together; the link up once, at 2.0 s.

```text
248.957 frames since the link came up: 1243 read, 1000 refused, 0 abandoned, 0 overruns, 0 other line errors
248.958 frames of the run: 1000 arrived, highest numbered 3000, 2000 missing, link up 1 time(s)
```

Every pull refused exactly once, none abandoned, a thousand numbered
frames arrived, no other line error, no reset on either side. The 243
frames read beyond the thousand are the link's own. These counters gave
only how many numbered frames arrived and the highest, which cannot show
that the thousand were the third frames and not some other thousand, so
the run was repeated with counters that can.

**The clean run, with arrivals by position.** Both images built from
clean source at `a56b3fb` (`0.0.0+ga56b3fb0`), the controller counting
each arrival by its position in a pull and whether its number was above
the one before. The sender was left to confirm its slot before the
controller was flashed; the module booted from `0x210000`. Controller
reset by the probe; the link up once, at 2.0 s.

```text
248.972 frames since the link came up: 1243 read, 1000 refused, 0 abandoned, 0 overruns, 0 other line errors
248.973 frames of the run: 1000 arrived, highest numbered 3000, 2000 missing, 0 not increasing, by position in a pull of 3: 0 0 1000, link up 1 time(s)
```

Every arrival was the third frame of its pull and none came out of order
or twice, so with a thousand of them and the highest 3 000, every third
frame arrived and no first or second frame did: recovery inside one
delimiter, a thousand times, with the fragment refused each time. The
2 000 missing are the frame cut on purpose and the frame it ran into, for
each pull.

**A rollback that was not asked for, once.** Between the two runs the cut
sender was flashed into `ota_0` while the bench controller was linked, and
the controller was reflashed about ten seconds later. The module came back
on the factory image: the bootloader logged `Defaulting to factory image`,
which it writes only for a slot still pending at a reset, so the freshly
written image had not confirmed itself before the controller's boot cycled
the module's rail. The same flash left alone for eight seconds confirmed
and booted from `0x210000`, and the same reflash of the controller against
the confirmed image did not roll it back. Not reproduced; the logs are
kept, and it is filed as #70 to run down with an `otadata` read-back
rather than inferred from the bootloader's text.

The pinned UART driver's hidden error paths remain unmeasured (#66); the
counters above are the reader's, which is what F-086 is about. After each
session both ordinary images were restored, last from `a56b3fb` with the
controller at boot count 138, the link up and the mailbox answering, the
log detached in non-blocking skip mode.

## 7. The boot record read back after a power cut (#59)

Board A rev A, the same ST-LINK, equipment disconnected, no analyser.
Controller image built from `bc12ddb` (#73), clean source, 107 152 bytes,
flashed by `just flash-controller` over the bootloader already on the part;
`o89-dev` from the same tree.

Before the flash, the image then on the part answered `just dev-ring` with
*the firmware does not know this operation*, boot count 143: a tool newer
than the firmware says so rather than reading garbage.

After the flash, `probe-rs reset` and then `just dev-reboot` (boot 144 to
145) each left one record, and board A was then powered off at the supply for
about ten seconds and powered on with no probe session open. Attached only
afterwards, `just dev-ring 4`:

```text
ring: next 166, oldest 1; newest first
seq      165  A  0x0601  at -  boot: power (on, down or brown-out); backup domain INVALID; RTC on its crystal; comms rail cycled
seq      164  A  0x0601  at -  boot: software reset; backup domain INVALID; RTC on its crystal; comms rail cycled
seq      163  A  0x0601  at -  boot: software reset; backup domain INVALID; RTC on its crystal; comms rail cycled
seq      162  A  0x0601  at -  boot, empty body: written before km43 0.3.0 gave the record its fields
```

The boot nobody watched is on the ring with its cause, and the probe
attached afterwards reads it: what 2026-09-20's *Not done* could not do.
`probe-rs reset` and the mailbox's reboot both request a system reset, so
both read as software resets, which is what `RCC.CSR` says for them.

The whole ring, `--count 1000`, read 165 records in 2.3 s over several
pages: seq 1 to 165 with no hole, 100 boots, 35 `0x0801`, 21 `0x0802` and
9 `0x0803` from the ladder benches, those with the empty body km43#32 still
owes them. Twenty records take 1.9 s, most of it the attach.

**The backup domain reads invalid on every boot, and here that says nothing
about the cell.** `reset::backup_domain` reads `RTC.ICSR.INITS`, which is set
once the calendar has been initialised, and nothing in this firmware
initialises it yet: setting the clock arrives with the time offers of M4
(#11). Until then the flag is honestly *the time is not known*, and it
cannot separate a dead backup cell from a clock nobody set. L-143's evidence
on the bench waits for the first set clock.

Not done: a watchdog and a panic were not provoked, so the last words keys
5 to 8 were read back only in host tests; the RTC's crystal flag was only
ever true.

## 8. Revalidating the Embassy pin move (F-090, #66)

Later the same day, on `david/embassy-main` at `261b705`. The firmware
workspace's Embassy crates move from the 0.6.0 releases to one revision of
Embassy's `main`, `77afe6cf`, for upstream's `844c4e7b`: the buffered UART
now leaves a byte in the hardware when its receive ring is full and masks
its receive interrupt until the task makes room, so `RTS` holds the module
off instead of the byte being dropped. `stm32-metapac` follows the revision
the HAL builds against, so the controller's own register writes and the
HAL's remain one crate. The comms firmware and the bootloader needed no
source change; the controller needed the renamed clock and register
constants, the UART constructors' new pin order and the interrupt binding
moved before the buffers.

The pin rules ask for the bench that revalidated it. Both runs below used
images built from clean source at `261b705`, flashed into `ota_0` through
the window with no wire.

**The flow-controlled frames run (F-087).**

```text
460.133 frames since the link came up: 10453 read, 0 refused, 0 abandoned, 0 overruns, 0 other line errors
460.133 frames of the run: 10000 arrived, highest numbered 10000, 0 missing, 0 not increasing, by position in a pull of 3: 3334 3333 3333, link up 1 time(s)
```

**The cut run (F-086).** The same result as on the old pin, which is what a
pin move has to show:

```text
289.055 frames since the link came up: 1283 read, 1000 refused, 0 abandoned, 0 overruns, 0 other line errors
289.055 frames of the run: 1000 arrived, highest numbered 3000, 2000 missing, 0 not increasing, by position in a pull of 3: 0 0 1000, link up 1 time(s)
```

Also observed: the link comes up 2.0 s after a controller reset, as before;
the ordinary images were restored and the module linked on its slot image;
the controller answered its mailbox at boot count 143.

**Not measured.** The backpressure itself. Showing it needs a receiving
task made late on purpose while the module sends, and a scope or an
analyser on `RTS` to see the line hold; a run in which nothing is lost
cannot tell a driver that holds the peer off from one that never filled its
ring. F-090 stays on the uncovered list until that run. The driver still
does not report the hardware's own receive faults, so F-087's no-overrun
condition remains unmeasured (#66).

**#70 reproduced.** Twice in this session, a slot flashed and then reset
within about six seconds came back on the factory image with the
bootloader logging `Defaulting to factory image`; the same flash left
fifteen seconds before any reset booted from `0x210000` every time. The
controller's reflash is what resets the module, by cycling its rail. Both
sequences are in #70.

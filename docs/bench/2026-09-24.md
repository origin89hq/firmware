## km43 0.6.0 on the board (#123)

**Before.** The controller was an earlier image at boot 170, epoch 1, no
client enrolled. `o89-dev store` read the network record as `Corrupt`, and
`challenges`, `volume`, `run` and `release` with it: bytes that are neither
blank nor a valid record, left by earlier images with other layouts. Since
#119 a damaged network record reads as no network, so on this part the
controller's section is unwritten.

**The controller flash left a watchdog boot record.** `just flash-controller`
ran from 11:51:03 to 11:51:15 UTC, the download taking 10.34 s. Boot 171's
record says `watchdog, nobody named`. `o89-dev reboot` then gave boot 172
with `software reset`, so the image itself resets cleanly. The 2026-09-23
flashes, of a 108 KB image, recorded `software reset` (#125). The cause first
read into this, a download outlasting the watchdog's 8 s, is contradicted by
the afternoon's session below.

**The old module refused the pairing report.** Between the two flashes the
module still ran `0.0.0+g9f928b96`. The controller's `PairingWindow` was
refused with 256 three times, 500 ms apart, then given up
(`RequestFailed(PairingWindow)`): that image predates L-193.

**The new pair links.** `just dev-flash-comms` ran from 11:51:59 to 11:53:53
UTC and ended `module reset normally`. The controller's log:

```text
131.350 [WARN ] link: BootNoise { count: 4932 }
131.350 [INFO ] link: up; the module is Peer { version: Version { major: 1, minor: 0 }, fw: "0.0.0+g0692bad3", hw: "controller-a rev A", boot_id: 2775231032, net_version: Some(0) }
131.403 [INFO ] record 0x0805: seq 198
```

`g0692bad3` is #123's commit before the squash, the same tree. The module's
boot text grew from 4 656 bytes to 4 932 with the new image.

**Thirteen minutes, nothing reset.** From the link-up at about 11:54 to
12:05:27 UTC the controller stayed at boot 172, and the ring holds no record
after seq 198: no `comms power cycled`, so the heartbeat ladder never fired.
A ten-minute `just attach-controller` from 11:55:05 printed nothing, which in
steady state is expected: the controller logs events, not heartbeats.

Not done: the case #123 exists for. The module reports `net_version` 0, so
nothing has to be cleared, and the controller logs no `NetConfig` push either
way, so this session cannot say whether one went out. Driving
`ClearUnwritten` on the board needs a module holding a foreign network, which
needs a network written to it, which needs a client that can send a signed
`SetConfig`; none exists yet. Wi-Fi off after a clear and back after a new
network, over repeated cycles, is untested for the same reason.
`o89-dev comms-listen` was not run.

State left: the controller and the module both on the tree of `0df9a53`,
the controller at boot 172.

## The watchdog record after a flash (#125), afternoon

Same board, probe and fixture. Controller images from `8e1a115` (#133,
175 904 bytes) and the same tree with an untracked file, which marks its
version `dirty` and so differs in its bytes; the module untouched on
`0.0.0+g0692bad3`. Registers read through `probe-rs read` and a throwaway
program on the `probe-rs` 0.32.0 library; nothing of it is committed.

**The freeze did not stop the record.** `just flash-controller` from #133,
which sets `DBG_IWDG_STOP` in `DBGMCU_APB_FZ1` before the download and
clears it after, took 10.56 s over the image of `0df9a53` at boot 172, up
since about 11:54. Boot 173 recorded `watchdog, nobody named`. The bit is
written, reads back `0x1000`, survives `probe-rs reset`, and read `0`
after every run that went through the wrapper, including one stopped by a
signal.

**The download does not run the watchdog.** `FLASH_OPTR` reads
`0xfffffeaa`: `IWDG_SW` set, so only software starts the IWDG. After the
reset and halt `probe-rs download` begins with, `IWDG_PR` reads 0 and
`IWDG_RLR` `0xfff`, their reset values, where the running image had 4 and
`0xf9f`. Held halted there for 12 s with the freeze clear, the core stayed
halted and no reset came. A `probe-rs download --verify` of 11.77 s with no
freeze left `RCC_CSR` at `0x14000000`, software and pin, no `IWDGRSTF`,
read before any reset.

**No flash since reproduced it.** Each of these recorded `software reset`:

| Flash | Replaced | Download | Freeze |
|---|---|---|---|
| `just run-controller`, same image | `8e1a115`, minutes up | 8.80 s | set |
| `probe-rs download` then `probe-rs reset`, same image | `8e1a115`, minutes up | 11.77 s | clear |
| the same two commands, the dirty image | `8e1a115`, minutes up | 10.35 s | clear |
| `just flash-controller`, back to `8e1a115` | dirty, minutes up | about 10.5 s | set |

The two flashes that left a watchdog record replaced an image that had run
for hours; every clean one replaced an image booted minutes before. Two
cases make that a lead, not a cause. The firmware ranks `IWDGRSTF` above
every other flag and the flags gather until a boot takes them, so the
watchdog fired somewhere between the old image's last boot and the new
image's first, and where is not known.

Not done: a flash over an image up for hours with `RCC_CSR` read between
the download and the reset, which says whether the watchdog fired before
the flasher's reset or in the new image's first boot, and in the second
case an attach straight after the reset to see where that boot stops.

State left: the controller on `8e1a115`, boot 179 at seq 211,
`DBGMCU_APB_FZ1` at 0.

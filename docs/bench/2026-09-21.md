# Bench session, 2026-09-21

Board A rev A, ST-LINK V2-1 `0671FF565357657287183750`, equipment
disconnected. Production flash layout, probe-rs 0.32.0, esptool 5.4.0
through the controller's download bridge, OTA-slot writes only. Measurement:
controller defmt counters over RTT, with probe-rs's default blocking RTT
mode. No analyser on the UART pair.

## The 483 missing frames (#63)

The original sender on `f949b776`, with corrected timeout accounting and
final-tally reporting on the controller, reproduced the issue after a fresh
controller reset:

```text
132.826 frames of the run: 9517 arrived, highest numbered 10000, 483 missing, link up 1 time(s)
```

The missing count was already 483 when the controller linked and stayed at
483 for the rest of the run. Before link-up, its writes repeatedly stalled
on CTS for 200 ms and it rebuilt the UART. The sender had already sent 500
numbered frames when the controller finished its handshake. Rebuilding the
UART also recreated the old bench counters, hiding earlier activity.

The sender started on its own `is_linked()`, which means the controller has
answered the module's statement. That does not mean the controller has
received the answer to its own statement. A batch of 100 worst-case frames
kept the module from reading the controller's requests during this interval;
the controller's transmit deadline is only 200 ms.

The corrected sender waits for a validated controller heartbeat before its
first batch. The controller sends heartbeats only after its own link-up.
The run still uses 100-frame batches at 921600 baud and the original receive
ring and wakeup threshold. Bench counters now survive UART reconstruction,
count timeout-driven abandonment, and report a changed final tally even if
no more bytes arrive.

The corrected flow-controlled run completed after a fresh reset:

```text
135.274 frames of the run: 10000 arrived, highest numbered 10000, 0 missing, link up 1 time(s)
```

There were zero frame refusals and zero abandoned frames after link-up.
The controller linked at 2.008 seconds, without the repeated CTS stalls.
An earlier 64-byte eager-read experiment introduced framing failures and
was removed before this run.

## Initial no-flow comparison: not qualified

The same corrected sender and a controller built with `no-flow`, after a
fresh reset, reached frame 10000 with 9881 numbered frames received: 119
missing. There were 120 framing refusals after link-up, zero abandoned
frames, and one link-up. Refusals include the link's own traffic, so their
count need not equal the number of missing numbered frames.

```text
141.270 frames since the link came up: 10002 read, 120 refused, 0 abandoned, 0 overruns, 0 other line errors
141.270 frames of the run: 9881 arrived, highest numbered 10000, 119 missing, link up 1 time(s)
```

Review identified a confounder in this first comparison: the controller
left RTS undriven while the sender still sampled it as CTS. Its losses do
not establish the no-flow requirement. The paired sender must explicitly
disable CTS; the follow-up below uses that configuration.

## Reviewed sender and paired no-flow comparison: not qualified

The sender's writes now have a 200 ms deadline. A write error or timeout
ends the run without retrying a number whose bytes may still be queued.
The repeated flow-controlled run with this sender completed at 134.167
seconds with 10000 numbered frames received, none missing, no framing
refusals or abandonments, and one link-up.

Flash verification passed, and the controller logged normal link-up after

## Subsequent review corrections

The second negative control also has a startup confounder: the sender can
receive a heartbeat from the flow-controlled bridge image before the
no-flow controller is started. Its sequence then continues into counters
that did not see the beginning. The 9883/10000 result above is historical
and does not qualify the paired no-flow behavior.

The bench now requires a validated controller firmware prerelease `bf` (flow)
or `bn` (no flow), matching the sender, as well as a
controller heartbeat. An ordinary bridge image cannot start either run.
Batches are reduced from 100 to four frames: at the 200 ms write deadline,
blocked writes take at most 800 ms per batch instead of up to 20 seconds,
which exceeded the eight-second watchdog period.

Host tests cover the mode gate, including ordinary and wrong-mode
controllers, and target builds check both variants. Removing the mode gate
fails its host assertion; restoring 100-frame batches fails the timing
assertion. The revised images were subsequently run on board A as recorded
below; the earlier hashes and results above identify different images.

Neither run rebooted or relinked. Before the no-flow run, the no-flow sender
was also paired with the flow-controlled bench controller: the link came
up and exchanged heartbeats through 23.040 seconds of controller uptime,
but no numbered frames arrived. This checks that the bridge/controller
mode mismatch does not start the burst early.

Both ordinary images from `a811e8ab` were then restored with flash
verification. The module linked normally at controller uptime 60.604
seconds after the final slot flash. RTT was detached in nonblocking skip
mode, leaving no logger or probe session attached.

The four-frame batches include waits for reads between bursts; these are
not continuous full-bandwidth saturation tests. RTT used probe-rs's default
blocking mode throughout both measured runs. No analyser was attached.
The pinned UART driver's hidden hardware-error and ring-overflow paths
remain unmeasured (#66), so this result does not complete F-087.

# Bench session, 2026-09-25

Board A rev A, ST-LINK V2-1 `0671FF565357657287183750`, equipment
disconnected, board B not attached, no wire on the module. The session ran
from 2026-09-24 22:00 UTC into the morning. The controller ran 6f459be and,
from about 00:30 UTC, 7597a4d's build, which is the same controller code.
Comms images were written into an OTA slot by `just dev-flash-comms` or
`o89-dev flash-comms <elf>` through the controller, by the knock. The BLE
client was the Mac, using `bleak` 20 cm from the board: a 20 s connect,
then service discovery, notify on TX, and 10 s connected. The client table
was empty (epoch 4), so every controller boot opened the first-enrolment
window for 120 s (F-091).

## Three traps that invalidated runs

Each looks like a firmware fault. The results below come only from runs
that avoided all three.

- **The controller sits halted after a probe reset (#155).** After
  `just reset-controller`, the core does not run until the next
  `just attach-controller`. Until then there is no link and no advertising,
  and the mailbox times out. Runs must keep an attach open from the reset
  onward. The cause and the fix are in the last section below.
- **Resetting right after a comms flash rolls the module back.** The new
  image confirms its slot only after its download window. A controller
  reset about 1 s after `module reset normally` cycled the module's rail
  first, and the module booted the other slot's Sep 22 image,
  `0.0.0+gce81fbe7`. That image has an old storage layout: it reported
  `net_version` 0, answered `NvsWriteFailed` and left `PairingWindow`
  unanswered. Wait about 25 s after a flash and check `fw` on every run.
- **An outside BLE client held the slots.** From about 01:55 UTC even the
  Wi-Fi-off control advertised nothing. A phone connecting without
  subscribing held both slots, which is fixed below.

## The access point reset the module every 6.8 s (#160)

While the window was open, the radio ran the access point beside the
station. The module rebooted every 6.8 s from link-up until the window
closed at 120 s, and the link came back each time under a new `boot_id`.
The reset reason, read back through a patched version string, was
`CoreSw` (0x03): a software reset or a panic. That rules out brown-out
and the watchdog. It reproduced on 7ed5cf6 (before #156) and on 8aebdab,
and it did not happen on 7597a4d, which drops the access point.

## BLE and a running station do not share the radio (#161)

V2 added forwarding of esp-radio's stubbed BLE coexistence callbacks, and
V3 added Wi-Fi modem sleep on top of it. Neither changed the result, so
neither shipped. Upstream: esp-rs/esp-hal#6397. Advertising lost at a
disconnect or a stop did not return until the module rebooted. Starting a
station and joining did not affect it.

## A stale vector catch held the core at its reset (#155)

Same board and probe, 12:20 to 12:42 UTC, the controller on 7597a4d's
build, boots 287 to 294. Registers read with `probe-rs read`, and the core's
registers with a throwaway probe-rs program that halts, reads and resumes.

Before any reset, DHCSR read `0x01040001` and DEMCR `0x00000401`:
`VC_CORERESET` and `VC_HARDERR` armed. `probe-rs attach` and `probe-rs run`
arm both, and neither disarms them when it ends. Their STM32G0 teardown
only turns the DBGMCU clock off, and a system reset keeps DEMCR. Every later
reset, the firmware's `Reboot` included, stops the core on its first
instruction. `probe-rs attach` resumes a halted core as it connects, which
is why the part always came back at the next attach.

- Reproduced three times out of three: DEMCR written to `0x401`, then
  `o89-dev reboot` from main timed out on `Ping`, with the core halted at
  PC `0x080000c0`, the reset handler at `0x00000004`.
- Each time, the fixed `o89-dev ping` said the core was held at its reset,
  ran it, and answered the next boot count (290, 291, 292). DEMCR read 0
  afterwards and RCC_APBENR1 `0x18400401`.
- With DEMCR at `0x401`, the fixed `o89-dev reboot` went from boot 292 to
  293, and `just reset-controller` through the wrapper left DEMCR at 0 and
  the part answered boot 294.
- `just attach-controller` with `--no-catch-reset` was not run.

A second failure turned up along the way. Twice the core hung in
`embassy_stm32::init`, at PC `0x080114a6`, polling PWR_CR1 for DBP. PWR_CR1
read `0x208`, RCC_APBENR1 read `0x08000000` (DBGEN set, PWREN clear) and
SYSCLK was still HSI16. It sat there for minutes, because the IWDG is armed
only after the clocks. The second time, the first version of the fix caused
it: that version ran the core and ended its session straight away. probe-rs's
STM32G0 sequences set DBGEN in RCC_APBENR1 when a session starts and clear it
when the session ends, and each is a read-modify-write over two SWD
transactions. One that lands just after a reset can write back the value it
read before the firmware set PWREN. The fix now keeps its session open
until the firmware serves its mailbox. `just reset-controller` recovered
the part both times. The hang before the watchdog is #168.

## Wi-Fi off with no network until a client scans (#166)

Board A, the same probe. Afternoon, 14:30 to 14:40 UTC. The controller was
on 2ecada9's build, boots 301 to 303. The module ran 3f083a9
(`0.0.0+g3f083a93`), flashed by `just dev-flash-comms`, and each run checked
`fw` in `link: up`. The client was the Mac with the origin89hq/apps bench
at b77d40f (`just bench`, CoreBluetooth, filtering on the KM43 service),
about a metre away. The network section was at version 4, holding no network
and country CA. `store write-epoch 9` cleared the client table, so boot 303
opened the first-enrolment window.

- **Window closed, no network, before any pairing (boot 301):** the Mac found the unit in
  1.9 s, connected and subscribed. On d1c3ade's image it found nothing in
  this state.
- **Pair in the window (boot 303):** connected in 0.6 s and paired, which closed
  the window. The Mac then reconnected with the window closed, in 2 s.
- **`WifiScan` accepted over that connection:** the Mac's link ended in a
  supervision timeout 1.43 s later, and the controller logged
  `CommsRebooted` at 17.191 s. That matches #170's 17.184 s. The reset
  is not one this change plans: with the result outstanding the station
  stays up.
- **After that reboot:** the Mac found the unit again in 3.7 s and read the section
  over BLE.
- **The network written over BLE:** `Stored` version 5 at 88.242 s. The
  Mac's link ended in a supervision timeout 4.4 s later, `CommsRebooted`
  at 93.894 s, and after the reboot the station joined. `dns-sd -G v4
  origin89.local` answered 192.168.0.180.

So the unit can be reached over BLE with no network, and onboarding over BLE
reaches a joined station. Both runs where the Wi-Fi driver started while a
client was connected over BLE also rebooted the module, once for a scan and
once for a join, and dropped the client. The reset site was not captured.
That is #170. This run cannot tell whether the link was lost to the reset
or to the radio.

Not done: the reboot back to Wi-Fi off after the last client leaves a
scan-only session, which the #170 reset preempted, and an iPhone.

State left: the module on `0.0.0+g3f083a93`, the station joined on network
version 5, the client table holding the Mac bench under epoch 9. The
iPhone's enrolment was dropped by the epoch rebase.

# Bench session, 2026-09-20

Board A rev A, the same unit and probe as the two sessions before it
(ST-LINK V2-1 `0671FF565357657287183750`, probe-rs 0.32.0), production
layout. Controller image 103 016 bytes and comms application image
112 832 bytes at `3039eed`; esptool 5.4.0 over the bench tool's socket
relay, ROM loader only (`--no-stub`), 115 200 baud on the bridge.
Instrument: the defmt log over RTT and the module's UART0 through the
bridge; no analyser on the bus.

**A cold start.** The board was unplugged overnight and had been unpowered
about twelve hours when the probe went back on. Everything in §1 and §2 was
read before anything was written, so it is the part as the night left it.
The two sessions before this one reset the part and cycled its rail but
never took its power away.

Every record this bench has written came back: the device secret written on
the 19th, epoch 1, the boot count, the panic record from boot 52, and the
client table stamped under the epoch. A real power-off, not a reset, and
the FRAM held.

The five that read `Corrupt` are the ones nothing has written yet. `Corrupt`
is not the same as absent: a slot nobody has written reads `Blank` and the
record reports `Absent`, and these read as neither blank nor valid because
the part still holds the self-test's bytes at those addresses, which
2026-09-19 §3 recorded before any of this was written. The night changed
none of them, and it is worth writing down that it was checked rather than
assumed: a record that had been written and came back `Corrupt` would be a
different session entirely.

## 3. The slot flash under the sector guard (F-084, F-085, #58)

the bytes a write means to change while `write-flash` erases every 4 KiB
sector the range touches, so the guard now judges the rounded range and
each write has to sit inside the partition it is for. That commit went in
after the probe came off the bench, so it had host tests and an argument
from alignment behind it and no run.

## 4. The ladder's carried cuts after a power-off (F-017, L-112)

The boot after the flash:

```text
0.000 [INFO ] boot: BootRecord { cause: Software, blame: None, rtc: Lse, backup: Invalid, revision: A, module_rail_cycled: true }
0.203 [INFO ] store: BootReport { epoch: epoch 1, clients: Some(Ok(Rebased)), boot: BootCount(105), boot_recorded: Ok(()), panic_recorded: None }
0.205 [INFO ] rail: 3 cuts in the last hour, carried and this boot's
```

Three cuts still counted in the last hour, on a part that spent the night
unpowered. That is F-017 as written rather than a fault: a boot carries
each cut as made at its own start, so the hour runs from the boot and not
from when the lines actually moved, and the rule already says a reset "can
keep a cut in the count for up to an hour longer than it was". A power-off
is the extreme of the same case, and there is nothing to age the window by:
`backup: Invalid` is the backup domain not surviving the night, so the part
has no wall clock that outlived its supply. The direction is the safe one —
the ladder reaches its next rung sooner, never later.

## Not done

The cold boot's own `BootRecord` was not read. The boot had already happened
by the time the probe was attached, and the ring could not have told it
afterwards: the firmware that ran wrote the `0x0601` record with an empty
body until origin89hq/km43#59 gave it one, so `cause`, `rtc` and `backup`
were on the probe's log and nowhere else. (This note first said the record
was on the ring and only undecodable, which was wrong.) What a genuine
power-on records for them is still unmeasured; §4's
record is a software reset, not the cold one. Tracked as #59. The
analyser was not on the bus, so what the firmware asked of the pins is on
the log and what the pins did is not. The whole-flash route and the killed
transfer were not repeated; 2026-09-19 §10 holds those, and nothing since
has touched the write order they exercise.

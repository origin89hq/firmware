# Bench session, 2026-09-19

Board A rev A, the same unit and probe as 2026-09-18 (ST-LINK V2-1
`0671FF565357657287183750`, probe-rs 0.32.0), the image at the head of the
M2 stack (`david/m2-recorder`), production layout unless said otherwise.
Instrument: the defmt log over RTT; no analyser on the bus tonight.

## 1. The supervisor from its own interrupt (F-007, F-008, H5)

The review of #40 named the gap: with the FRAM and the NOR driven by
blocking calls behind the async seams, a transfer that never returned
would hold the thread executor, the supervisor on it would never run, and
the watchdog would reset the part with no name to blame. The supervisor
runs from its own interrupt now, `CEC`, at the lowest interrupt priority,
above the thread executor.

The production image boots as before, the supervisor feeding from the
interrupt and the recorder opening the ring:

```text
0.100 [INFO ] store: BootReport { epoch: no epoch: both slots damaged, clients: None, boot: BootCount(49), boot_recorded: Ok(()), panic_recorded: None }
0.206 [INFO ] rail: settled, EN released
0.238 [INFO ] ring: open at block 42 offset 52, next seq 3, oldest Some(1), damage Damage { failed_crc: 0, closed: 0 }
0.241 [INFO ] boot record: seq 3
```

The bench image's starve proof no longer stops checking in cooperatively:
it spins the thread executor with `nop`s, so nothing on that executor runs
again. The proof chain, three boots in one session with the probe's
vector catches off:

```text
0.100 [INFO ] store: BootReport { ..., boot: BootCount(50), boot_recorded: Ok(()), panic_recorded: None }
15.101 [WARN ] watchdog proof: the control tick blocks the executor on purpose; the part resets in about 8 s and the next boot names it
19.200 [ERROR] feed withheld: Control is 99 ms past its window; reset follows
26.200 [WARN ] feed withheld for 7 s; reset pending
0.000 [INFO ] boot: BootRecord { cause: Watchdog, blame: Some(Blame { task: Control, overdue: Millis(99) }), rtc: Lse, backup: Valid, revision: A, module_rail_cycled: true }
0.102 [INFO ] store: BootReport { ..., boot: BootCount(51), boot_recorded: Ok(()), panic_recorded: Some(Landed) }
0.000 [ERROR] the previous run panicked at file 0xa70c05b0 line 345
0.000 [INFO ] boot: BootRecord { cause: Software, blame: None, ... }
0.102 [INFO ] store: BootReport { ..., boot: BootCount(52), boot_recorded: Ok(()), panic_recorded: Some(Landed) }
```

With the thread executor held from 15.1 s, the supervisor named Control
at 19.2 s, 5.1 s after that task's last check-in at 14.1 s and 4.1 s
after the executor was blocked, and counted the seven seconds to the
reset; the boot after the watchdog read the blame. The generator lines
were not on an instrument; the firmware's own sampling of the contact is
all this session says about them. That is
the case the 18th's observation did not cover, when the recorder was
blocked in an `await` and the executor was free. The boot after the
deliberate panic read its site, and the panic record landed on the FRAM
under the boot that found it (F-008 on the part, `panic_recorded:
Some(Landed)`), which the 18th could not show because the store was not
there yet.

The bootloader and the production image were flashed back after the
chain; the board is in the production layout.

## 2. The NOR identified once ready

A reset in the middle of a program or an erase leaves the W25Q128JV
powered and busy, and a busy part ignores the identification. The
recorder waits for the part to report ready, against the erase deadline,
before it asks; the boots above identified it at 0.101 s as before.

## 3. The bench tool through the mailbox (#4, F-014)

recorder serves a mailbox in the last 4 KB of RAM and the host tool
(`crates/o89-dev`, probe-rs 0.32.0 as a library) drives it over SWD while
the firmware runs; nothing here was written around the firmware.

## 4. The link task on USART1, and the ladder for real (F-030, F-006, L-110, L-111, H3)

The image of `david/m3-link-controller`, production layout, the same
probe. The module carries the old scan app, which talks at the link's
baud and speaks nothing `km43` frames, so nothing on the other end can
state itself: the controller's side of the ladder runs for real, and
every byte the module sends is counted as noise.

**The DMA ring first, and it overran from the first byte.** USART1's
receive on `DMA1` channel 2 and its transmit on channel 1, each on an
interrupt line of its own, so as not to repeat the recorder's finding on
the shared `DMA2` line (#39):

```text
0.207 [INFO ] link: the rail settled; USART1 up
0.227 [WARN ] link: receive overrun
0.227 [WARN ] link: receive overrun
…
```

16 102 overruns in 190 s, one every read, the ring never draining the
data register: the same failure as I2C2 and SPI1 on `DMA2`, on `DMA1`
lines of their own, which points below the interrupt lines, at the DMAMUX
routing or the channel setup in `embassy-stm32` 0.6.0 for this part
(#39). The link's own machinery ran through it: the statement retried
and given up every two seconds, the cut at sixty seconds, the cycle
recorded, the ROM text counted.

**The interrupt-driven UART, no overrun in three minutes.** The same
image with `BufferedUart` and rings of two frames in and one out:

```text
0.207 [INFO ] rail: settled, EN released
0.207 [INFO ] link: the rail settled; USART1 up
0.345 [INFO ] record 0x0601: seq 19
1.827 [WARN ] link: RequestFailed(0x60)
3.867 [WARN ] link: RequestFailed(0x60)
…
60.378 [WARN ] link: asking the rail for a cut
60.382 [WARN ] rail: cutting for 5000 ms, cycle 1 in the last hour
60.383 [WARN ] link: PowerCycled { count: 1 }
60.449 [INFO ] record 0x0802: seq 20
65.382 [WARN ] rail: power restored, 1 cycles in the last hour
65.482 [INFO ] rail: settled, EN released
65.482 [INFO ] link: the rail settled; USART1 up
65.483 [INFO ] link: RomText { count: 12662 }
125.496 [WARN ] link: asking the rail for a cut
125.503 [WARN ] link: PowerCycled { count: 2 }
125.548 [INFO ] record 0x0802: seq 21
130.603 [INFO ] link: RomText { count: 12205 }
190.743 [WARN ] link: asking the rail for a cut
190.763 [WARN ] link: PowerCycled { count: 3 }
190.848 [INFO ] record 0x0802: seq 22
```

Zero overruns. The `LinkUp` goes out the moment the rail settles and is
given up after its three attempts, then again every two seconds, ninety
times in three minutes; the cut comes 60.17 s after the rail settled,
the rail is off 5.0 s and settles 100 ms after it returns, and the next
cut comes 60.0 s after that. Each cycle is a class A record on the ring,
sequences 20 to 22, its count on the probe until km43#32 gives the
record a body. The ROM-text count per module boot is twelve thousand,
which is the old app talking and not the ROM; the count near one that
F-031 expects comes with the comms firmware of the next cut. The lines
were not scoped: what the firmware asked of the pins is on the log, what
the pins did is not.

The controller image is 85 728 bytes, 25 616 more than at 633cbee: the
state machine, `km43`'s link-local bodies and CBOR, and the buffered
UART driver.

**The rail before the store.** After the review of #45, the boot powers
the rail before any bus and waits its settling before the FRAM, so a
reset inside a cut adds only the path to the rail (F-005). The module
carries the comms firmware of #47:

```text
0.000 [INFO ] boot: BootRecord { cause: Software, …, revision: A, module_rail_cycled: true }
0.000 [INFO ] rail: powering the module, EN held low
0.201 [INFO ] store: BootReport { epoch: epoch 1, …, boot: BootCount(82), boot_recorded: Ok(()), … }
0.228 [INFO ] rail: settled, EN released
0.228 [INFO ] link: the rail settled; USART1 up
1.810 [WARN ] link: RequestFailed(0x60)
2.006 [INFO ] link: RomText { count: 1140 }
```

The rail goes on in the log's first millisecond, and the store follows
after the 100 ms settle. The log's clock starts with the clocks, so the
path before it is not measured: the bootloader, the reset vector and the
clock start, with no bus and no wait but the oscillator's. The first
`LinkUp` falls in the module's window and is given up; the next is
answered, and nothing failed or was cut in the 43 s after it.

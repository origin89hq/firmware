# Bench session, 2026-09-19

Board A rev A, the same unit and probe as 2026-09-18 (ST-LINK V2-1
`0671FF565357657287183750`, probe-rs 0.32.0), the image at the head of the
M2 stack (`david/m2-recorder`), production layout unless said otherwise.
Instrument: the defmt log over RTT; no analyser on the bus tonight.

## 1. The supervisor from its own interrupt (F-007, F-008, H5)

The review of #40 named the gap: with the FRAM and the NOR driven by
blocking calls behind the async seams, a transfer that never returned
would hold the thread executor, the supervisor on it would never run, and
the watchdog would reset the part with no name to blame. The supervisor
runs from its own interrupt now, `CEC`, at the lowest interrupt priority,
above the thread executor.

The production image boots as before, the supervisor feeding from the
interrupt and the recorder opening the ring:

```text
0.100 [INFO ] store: BootReport { epoch: no epoch: both slots damaged, clients: None, boot: BootCount(49), boot_recorded: Ok(()), panic_recorded: None }
0.206 [INFO ] rail: settled, EN released
0.238 [INFO ] ring: open at block 42 offset 52, next seq 3, oldest Some(1), damage Damage { failed_crc: 0, closed: 0 }
0.241 [INFO ] boot record: seq 3
```

The bench image's starve proof no longer stops checking in cooperatively:
it spins the thread executor with `nop`s, so nothing on that executor runs
again. The proof chain, three boots in one session with the probe's
vector catches off:

```text
0.100 [INFO ] store: BootReport { ..., boot: BootCount(50), boot_recorded: Ok(()), panic_recorded: None }
15.101 [WARN ] watchdog proof: the control tick blocks the executor on purpose; the part resets in about 8 s and the next boot names it
19.200 [ERROR] feed withheld: Control is 99 ms past its window; reset follows
26.200 [WARN ] feed withheld for 7 s; reset pending
0.000 [INFO ] boot: BootRecord { cause: Watchdog, blame: Some(Blame { task: Control, overdue: Millis(99) }), rtc: Lse, backup: Valid, revision: A, module_rail_cycled: true }
0.102 [INFO ] store: BootReport { ..., boot: BootCount(51), boot_recorded: Ok(()), panic_recorded: Some(Landed) }
0.000 [ERROR] the previous run panicked at file 0xa70c05b0 line 345
0.000 [INFO ] boot: BootRecord { cause: Software, blame: None, ... }
0.102 [INFO ] store: BootReport { ..., boot: BootCount(52), boot_recorded: Ok(()), panic_recorded: Some(Landed) }
```

With the thread executor held from 15.1 s, the supervisor named Control
at 19.2 s, 5.1 s after that task's last check-in at 14.1 s and 4.1 s
after the executor was blocked, and counted the seven seconds to the
reset; the boot after the watchdog read the blame. The generator lines
were not on an instrument; the firmware's own sampling of the contact is
all this session says about them. That is
the case the 18th's observation did not cover, when the recorder was
blocked in an `await` and the executor was free. The boot after the
deliberate panic read its site, and the panic record landed on the FRAM
under the boot that found it (F-008 on the part, `panic_recorded:
Some(Landed)`), which the 18th could not show because the store was not
there yet.

The bootloader and the production image were flashed back after the
chain; the board is in the production layout.

## 2. The NOR identified once ready

A reset in the middle of a program or an erase leaves the W25Q128JV
powered and busy, and a busy part ignores the identification. The
recorder waits for the part to report ready, against the erase deadline,
before it asks; the boots above identified it at 0.101 s as before.

## 4. The link task on USART1, and the ladder for real (F-030, F-006, L-110, L-111, H3)

The image of `david/m3-link-controller`, production layout, the same
probe. The module carries the old scan app, which talks at the link's
baud and speaks nothing `km43` frames, so nothing on the other end can
state itself: the controller's side of the ladder runs for real, and
every byte the module sends is counted as noise.

**The DMA ring first, and it overran from the first byte.** USART1's
receive on `DMA1` channel 2 and its transmit on channel 1, each on an
interrupt line of its own, so as not to repeat the recorder's finding on
the shared `DMA2` line (#39):

```text
0.207 [INFO ] link: the rail settled; USART1 up
0.227 [WARN ] link: receive overrun
0.227 [WARN ] link: receive overrun
…
```

16 102 overruns in 190 s, one every read, the ring never draining the
data register: the same failure as I2C2 and SPI1 on `DMA2`, on `DMA1`
lines of their own, which points below the interrupt lines, at the DMAMUX
routing or the channel setup in `embassy-stm32` 0.6.0 for this part
(#39). The link's own machinery ran through it: the statement retried
and given up every two seconds, the cut at sixty seconds, the cycle
recorded, the ROM text counted.

**The interrupt-driven UART, no overrun in three minutes.** The same
image with `BufferedUart` and rings of two frames in and one out:

```text
0.207 [INFO ] rail: settled, EN released
0.207 [INFO ] link: the rail settled; USART1 up
0.345 [INFO ] record 0x0601: seq 19
1.827 [WARN ] link: RequestFailed(0x60)
3.867 [WARN ] link: RequestFailed(0x60)
…
60.378 [WARN ] link: asking the rail for a cut
60.382 [WARN ] rail: cutting for 5000 ms, cycle 1 in the last hour
60.383 [WARN ] link: PowerCycled { count: 1 }
60.449 [INFO ] record 0x0802: seq 20
65.382 [WARN ] rail: power restored, 1 cycles in the last hour
65.482 [INFO ] rail: settled, EN released
65.482 [INFO ] link: the rail settled; USART1 up
65.483 [INFO ] link: RomText { count: 12662 }
125.496 [WARN ] link: asking the rail for a cut
125.503 [WARN ] link: PowerCycled { count: 2 }
125.548 [INFO ] record 0x0802: seq 21
130.603 [INFO ] link: RomText { count: 12205 }
190.743 [WARN ] link: asking the rail for a cut
190.763 [WARN ] link: PowerCycled { count: 3 }
190.848 [INFO ] record 0x0802: seq 22
```

Zero overruns. The `LinkUp` goes out the moment the rail settles and is
given up after its three attempts, then again every two seconds, ninety
times in three minutes; the cut comes 60.17 s after the rail settled,
the rail is off 5.0 s and settles 100 ms after it returns, and the next
cut comes 60.0 s after that. Each cycle is a class A record on the ring,
sequences 20 to 22, its count on the probe until km43#32 gives the
record a body. The ROM-text count per module boot is twelve thousand,
which is the old app talking and not the ROM; the count near one that
F-031 expects comes with the comms firmware of the next cut. The lines
were not scoped: what the firmware asked of the pins is on the log, what
the pins did is not.

The controller image is 85 728 bytes, 25 616 more than at 633cbee: the
state machine, `km43`'s link-local bodies and CBOR, and the buffered
UART driver.

**The rail before the store.** After the review of #45, the boot powers
the rail before any bus and waits its settling before the FRAM, so a
reset inside a cut adds only the path to the rail (F-005). The module
carries the comms firmware of #47:

```text
0.000 [INFO ] boot: BootRecord { cause: Software, …, revision: A, module_rail_cycled: true }
0.000 [INFO ] rail: powering the module, EN held low
0.201 [INFO ] store: BootReport { epoch: epoch 1, …, boot: BootCount(82), boot_recorded: Ok(()), … }
0.228 [INFO ] rail: settled, EN released
0.228 [INFO ] link: the rail settled; USART1 up
1.810 [WARN ] link: RequestFailed(0x60)
2.006 [INFO ] link: RomText { count: 1140 }
```

The rail goes on in the log's first millisecond, and the store follows
after the 100 ms settle. The log's clock starts with the clocks, so the
path before it is not measured: the bootloader, the reset vector and the
clock start, with no bus and no wait but the oscillator's. The first
`LinkUp` falls in the module's window and is given up; the next is
answered, and nothing failed or was cut in the 43 s after it.

## 5. The flashing path through the controller (F-038, F-034, H8)

Board A revision A, controller image 93 992 bytes at the end of the
session, comms image 110 736; probe-rs 0.32, esptool 5.4.0 over the
bench tool's socket relay, ROM loader only (`--no-stub`), 115200 baud on
the bridge. The module's UART0 is bridged to two rings in the mailbox
that the host reaches over SWD.

**Two lamps lit, and a controller that ran nothing.** Before the first
run, LED2 and LED3 were fully lit and the mailbox answered nothing. The
core was halted at probe-rs's flash loader in RAM (PC `0x2000001e`, the
loader's `bkpt` pair, every other register at its reset value):
`probe-rs download` leaves the part there, and `just flash-controller`
never reset it. Every pin an analog input, so two of the three RS-485
transceivers read their floating DI low and drove their buses low, the
lamps showing it, which is hardware#28 observed rather than inferred; the
third DI floated high. Both recipes now end with a reset.

**The ROM never waits in its loader by itself.** The module's flash had
lost its app to an earlier run that erased and then dropped esptool's
socket, and kept its bootloader and partition table. Listened to through
the bridge, the ESP-IDF bootloader printed its table, `No bootable app
partitions`, and rebooted, forever (`rst:0x3 (LP_SW_HPSYS)`), and the
ROM's loader was never entered. The no-knock entry the tool had, built on
the belief that an empty module waits in its loader, was removed.

**The strap route.** With IO9 driven low by PC3 across an EN reset from
the rail sequencer, held 50 ms with EN and 100 ms after its release, the
ROM printed `boot:0x0 (USB_BOOT)` and `wait usb download` and nothing
after: the strap is read, and with IO8 floating it selects the USB-only
loader, as on 2026-09-14. The bridge caught the banner only once the
sequencer reported the rail settled at EN's release rather than at the
strap's; before that change the run showed 0 bytes. With the wire from
CN11 pin 2 held on U8 pad 10, the same reset entered the serial loader
and esptool wrote 176 240 bytes at `0x0` in 25.1 s (56.2 kbit/s), hash
verified, and the module booted the image: `link: up` with
`fw: o89-comms 0.0.0`, `boot_id 0x5939bb7a`, `RomText 1141`. One
attempt of three failed on the wire's contact (`No serial data
received`), the next succeeded.

**The window route, and the watchdog.** Through the window with no
wire, the module answered the knock and entered its loader
(`the module is entering download mode; bridging at 115200 baud`),
esptool connected, erased `0x0` to `0x2bfff` in 0.43 s, and then the
socket went quiet: `No more data to read from the serial port`, the
controller logging `3 bytes from the module were lost on a full ring`
9.2 s after the module's reset. The module's RTC watchdog, armed at 8 s
as the firmware's first statement (F-032), lives in the LP domain and
outlived the software reset into the ROM, whose loader does not feed it:
it reset the chip out of the loader after the erase and before the
first write, and the app was gone again. The window now disarms it
before the reset (F-034). The module was recovered by the strap route
with the wire, 176 272 bytes in 25.1 s, and then flashed through the
window with no wire: 176 272 bytes in 24.7 s (57.1 kbit/s), hash
verified, the module reset normally, and `link: up` 1.8 s after the rail
settled with `boot_id 0xce6de451` and `RomText 1142`. Then five more in
a row through the window, unattended: 24.6 to 24.7 s each, every hash
verified, the link up after each with a new `boot_id` (`0xf80a11fd`,
`0x478725ac`, `0x4484fd41`, `0x35e171f2`, `0xcef6ddc0`), nothing lost on
the rings. The ROM-text count per module boot is about 1 140 with this
bootloader's log, and F-031's baseline is now that number rather than
one.

**A host that dies with the bridge open.** A host that exits without
giving the module back, as one that crashed or lost its probe would
(`dev-comms-listen --leave-open`), left the module held in its ROM with
the bridge open. Killing the tool instead left the ST-Link's USB
interface claimed with no process holding it, and only a replug freed
it, so the fault is injected by a clean exit. Two answers, each run on
the board:

- A flash through the window 4 s later reclaimed the bridge
  (`another download reclaims the bridge`), wrote 176 272 bytes in
  24.6 s with the hash verified, gave the module back, and the link was
  up 1.8 s after. An earlier image lost the answer to the host's
  request for the normal state, because two reports went out back to
  back and the second replaced the first; reports now go out once per
  request, under the request's number.
- With nothing after it, the bridge closed by itself 60 s after the
  host's last lease renewal (`the host's lease on the bridge lapsed 60 s
  ago`), the module was reset normally, and the link was up 1.8 s
  later. An earlier image measured the idle from any byte on the bridge
  and never closed, because the module's application talks on the link
  whether anyone listens or not; the host now renews a lease word in the
  mailbox about once a second while it reads the bridge, and only that
  counts.

The controller image grows from 87 144 bytes at the comms cut to
93 992 (+6 848): the bridge, the knock, the strap route, the mailbox's
rings, and the bridge's lease and reclaim. The comms image grows by 32
bytes to 110 736 for the disarm.

## 6. The link measured by answers (L-033, L-100, F-038)

After review the link rules changed at the source (origin89hq/km43#52):
a side is linked once its own `LinkUp` is answered, and silence is
measured from the peer's last answer to one of its requests, so a comms
processor that talks but cannot hear is cut at sixty seconds instead of
never. Both firmwares follow it; controller image 94 520 bytes, comms
image 110 704.

Against the previous comms image, which still linked on either
statement, the new controller linked at 1.98 s. With both new images,
flashed through the window with no wire, 176 240 bytes in 24.6 s and
the hash verified, the link came up once, 1.8 s after the module
returned, `RomText 1141`. The run showed two faults of the first
round-trip build, both fixed before this note: the adapter logged the
link up when the peer's own statement was recorded, which no longer
links; and a flash left the state machine linked while the module sat
in its ROM, so the first tick after the bridge counted forty seconds as
silence and recorded comms link lost (`0x0801`). The bench now takes
the module explicitly: every connection drops as `ModuleTaken`, nothing
is recorded as lost, and the controller logs the reason with the
verdict as L-192 asks (`EnterDownload (bench) answered entering`).

## 7. The comms firmware on `o89-comms-core`, and the module's lines through its reset (#47, F-033, L-015, L-100, L-120, L-192)

The images of `b0bda0d`, the head of the stack after the second review
of #44 to #51: the comms firmware boots from the HAL's bare entry and
enters its executor only after the window; its window and link are
`o89-comms-core`'s, on the link mechanics `o89-link` shares with the
controller; the knock takes only an answer under its own id and a
refusal is reported as one (L-192); the rail comes on before the store
(F-005). Controller image 97 048 bytes, comms image 112 832.

**A reset loop, and the window through it.** A build of this cut that
confirmed its OTA slot three times over and reset when it could not read
the slot's state was flashed first. On this module, written as the
factory image with no slot selected, that read is an error by design, so
the module reset after every window: the controller logged its `LinkUp`
failing every two seconds, the cut at sixty seconds, and 42 034 bytes of
boot text in the minute before it, a boot every 1.6 s. The window ran on
every one of those boots and answered the knock through the loop: the
corrected image, which reads no selected slot as nothing to confirm, was
written and hash-verified with no wire, and linked. The recovery path
held against a firmware of ours that could not boot.

**The flash, answered under the knock's own id.** The controller logged
`download (Bench) by Knock`, then `EnterDownload (Bench) answered
entering` 270 ms after it released `EN`, the answer from the window of
the image before, the first built from the bare entry; the recipe built
the images first, and esptool wrote 178 368 bytes in 24.9 s, the hash
verified. Given back, the module linked 1.78 s after its reset with
`fw: "0.0.0+gb0bda0d6"`, and nothing failed, dropped or was cut in the
minute read after it. The ROM text on that boot counted 915 against
1 142 on the controller's own boot a minute later; the count is of runs
the reader drops in text at another baud, and moves with that text.

**The comms side stays linked on answers to its own beats.** A build of
the controller that is not committed logged each frame the module sent,
by opcode and request id. After the link came up at 2.0 s the module
sent its `Heartbeat` (`0x61`) and answered the controller's (`0xE1`)
every 2 s, 14 of each in the 26 s read, and not one `LinkUp`: its
six-second timer, which only the answer to one of its own beats resets
(L-100, L-120), never fired.

**The module's lines through its reset.** The same build sampled `PB4`,
the controller's CTS on the module's GPIO5, and `PB7`, its RX on the
module's GPIO16, every 500 µs for four seconds from the rail's
switch-on, each read under the controller's internal pull-up and then
its pull-down: a line that follows both is floating, one that reads the
same under both is driven.

```text
0.000 rail: powering the module, EN held low
0.000 probe: PB4 floating; PB7 floating
0.223 rail: settled, EN released
0.231 … 0.393: PB7 driven high, low and floating in turn; PB4 floating
0.394 probe: PB4 driven low; PB7 driven high
```

Held in reset, the module drives neither line, as the ESP32-C6
datasheet's table 2-1 has it. Released, GPIO16 carries the ROM's
banner, sampled mid-character, and GPIO5 floats for 171 ms, until the
firmware's second statement takes it as RTS and asserts it; both are
driven from then on. The images of `a43f580` and `856f06b`, before the
bare entry, read 186 and 185 ms. The controller's first `LinkUp` went
out into that floating CTS and was not held past its deadline: no stall
was logged. A brown-out that resets the module is the first state, and
with the rail off the controller's USART1 is down (F-003).

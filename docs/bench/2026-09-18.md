# Bench session, 2026-09-18

Controller board A revision A, the 2026-09-09 export, on an ST-LINK V2-1
(serial `0671FF565357657287183750`) driven by probe-rs 0.32.0. Board B was
not on CN9 as far as the log can tell: `FEEDBACK` read open throughout, and
the contact was not scoped. No scope or logic analyser was on the bench;
the instrument is the probe's RTT carrying the defmt log.

Firmware: `main` at 4a71e2d plus the two fixes this session produced,
committed as 8eac737, which every image below was built from. The bench
image (build id `2b62e5f2f764c0f4953575195a3d1f64630d0acb`) links at
0x08000000 and carries the proofs; the production image (build id
`edfc0d16d15d70c3a9908533f161f80042936139`, 14 984 bytes) links at
0x08002000 behind the bootloader (448 bytes, the same bytes in both banks).

## 1. The watchdog proof and the panic proof (F-007, F-008, H5)

`just run-controller-bench`, then `just attach-controller` after each reset,
because `probe-rs run` and `probe-rs attach` both end when the target
resets; the next boot's lines were waiting in the RTT buffer each time.
Three boots in a row from the first two runs, which predate the tick
stamp on the log, verbatim with the source locations dropped:

```text
boot 1
[INFO ] boot: BootRecord { cause: Software, blame: None, rtc: Lse, backup: Valid, revision: A, module_rail_cycled: true }
[INFO ] rail: powering the module, EN held low
[INFO ] rail: settled, EN released
[INFO ] generator contact: Open
[WARN ] watchdog proof: the control tick stops checking in on purpose; the part resets in about 8 s and the next boot names it
[ERROR] feed withheld: Control is 100 ms past its window; reset follows

boot 2
[INFO ] boot: BootRecord { cause: Watchdog, blame: Some(Blame { task: Control, overdue: Millis(100) }), rtc: Lse, backup: Valid, revision: A, module_rail_cycled: true }
[INFO ] rail: powering the module, EN held low
[INFO ] rail: settled, EN released
[INFO ] generator contact: Open
[WARN ] panic proof: panicking on purpose; the part resets and the next boot names the site

boot 3
[ERROR] the previous run panicked at file 0xa70c05b0 line 279
[INFO ] boot: BootRecord { cause: Software, blame: None, rtc: Lse, backup: Valid, revision: A, module_rail_cycled: true }
[INFO ] rail: powering the module, EN held low
[INFO ] rail: settled, EN released
[INFO ] generator contact: Open
```

What the records say. The supervisor withheld the feed 100 ms after the
control tick's 5 s window closed, which is one supervisor period, and the
part reset; the next boot read the reset as the watchdog's and named the
task and the overdue from the last words. The panic went through the
production handler, not `panic-probe`: the next boot read the reset as a
software one and reported the site, and `0xa70c05b0` is FNV-1a of
`o89-controller/src/main.rs`, the path the compiler holds, with line 279
the `panic!` in `panic_on_purpose`. The third boot ran on. Every boot
reported the RTC on the LSE with its backup domain valid, so the crystal on
this board runs and is what the HAL selected (F-010), and every record
says the reset cycled the module rail, which revision A does (F-014).

### The watchdog's interval, measured

A third run with the log stamped by the tick and the supervisor logging
each whole second the feed stays withheld:

```text
14.000  the control tick's last check-in (it stops at 15.000)
15.000 [WARN ] watchdog proof: the control tick stops checking in on purpose; the part resets in about 8 s and the next boot names it
19.000  the supervisor's last pet: the window closes at exactly 5 s
19.100 [ERROR] feed withheld: Control is 100 ms past its window; reset follows
20.100 [WARN ] feed withheld for 1 s; reset pending
...
26.100 [WARN ] feed withheld for 7 s; reset pending
        no 8 s line: the part reset between 26.100 and 27.100
```

So the watchdog, set to 8 s, reset the part between 7.1 and 8.1 s after its
last feed, which is the LSI running inside its tolerance. F-016's budget
uses the datasheet's slow bound of 8.8 s and this run does not move it.
The next session reads it to the tenth from a scope on the reset.

## 2. The production layout boots through the bootloader (F-001, H1 in part)

`just flash-boot`, `just flash-controller`, `just reset-controller`, then
`just attach-controller`. The first words read back from the part:

```text
08000000: 20024000 080000c1    the bootloader, bank 1
08002000: 20024000 08002101    the application: stack at the top of RAM, reset just past the vector table and the build-id note
08040000: 20024000 080000c1    the bootloader, bank 2
```

After the reset the application's boot record came up on the probe with the
rail sequence and the contact behind it, so the bootloader's plausibility
check accepted the real image's words, the jump landed, the application
set its own `VTOR` and its interrupts run. The lines themselves were not
scoped; that is the rest of H1 and waits for board B on CN9 and a scope.

## 3. The store and the ring on the board (F-020, F-021, F-023, H4, H5)

Same board, same probe, the production layout, the image at the head of
the M2 stack (`david/m2-recorder`). The FRAM is read in `main` before any
output moves and the recorder task opens the ring on the NOR.

The first image used the HAL's DMA drivers for both buses. The FRAM read
timed out after a second and the recorder then hung in the NOR's first SPI
transfer and never checked in, which the supervisor caught:

```text
1.007 [ERROR] store: the FRAM did not answer: Bus(Timeout); booting without it
31.109 [ERROR] feed withheld: Recorder is 101 ms past its window; reset follows
38.109 [WARN ] feed withheld for 7 s; reset pending
```

The part reset on the watchdog about eight seconds later and the boot
after it read `cause: Watchdog`. The firmware sampled the generator
contact open before and after (`generator contact: Open`, the `FEEDBACK`
input through its pull-up); the `RUN` and `KICK` lines themselves were
not on an instrument tonight, so whether they moved is not measured here.
That is H5's argument run for real by a bus that hung, with one thing to
say precisely: the recorder was blocked in a DMA transfer's `await`, so
the executor was free and the supervisor on it could run. It proves the
cooperative case. Both drivers are blocking behind the async seams now,
the self-test's path since 2026-09-14, and a blocking call that never
returned would hold the executor itself; that case is answered by the
supervisor moving to its own interrupt, and proved on 2026-09-19. The DMA
path is filed as a question on its own.

The second image opened the ring with a scan that hunted every block
whole for a magic. This NOR still holds the self-test's bytes in every
sector, and 3712 blocks of them is fifteen megabytes over SPI: the boot
never got past `recorder: opening the ring` and the watchdog reset the
part every eight seconds, boot count climbing by one each time. A probe
reads one record's reach at a block's start now, and:

```text
0.100 [INFO ] store: BootReport { epoch: no epoch: both slots damaged, clients: None, boot: BootCount(47), boot_recorded: Ok(()), panic_recorded: None }
0.101 [INFO ] recorder: identification answered Ok([239, 64, 24])
0.206 [INFO ] rail: settled, EN released
0.690 [INFO ] ring: open at block 42 offset 0, next seq 1, oldest None, damage Damage { failed_crc: 0, closed: 0 }
0.693 [INFO ] boot record: seq 1
```

The FRAM answers: the boot count had climbed through every reset of the
afternoon and landed each time (F-020). The epoch reads *both slots
damaged* because the self-test's record sits where the map puts the
epoch, which is the answer the design gives to bytes it did not write:
nothing is enrolled and nothing derives until `o89-dev` writes an epoch.
The NOR identifies as `EF 40 18`. The ring found no record of its own in
forty-two blocks of foreign bytes, started in the first erased one, erased
the block ahead, and landed the first boot record 0.6 s after boot while
the rail task kept its 100 ms tick. The next boot found that record and
continued the sequence.

## What the session found and changed

- A reset the probe requests reads as a software reset: the board has no
  `NRST` (origin89hq/hardware#29), so the probe uses the core's reset
  request. The proof chain was keyed on the reset cause and never started
  on the first run; it now keys on the last words, which say which step a
  boot is whatever reset it. Fixed in 8eac737.
- `FEEDBACK` read closed on the very first read after the pull-up was
  configured and open a second later: a read in the microsecond after the
  pull-up is switched on sees the line before it has risen. The first read
  is the first tick's now. Fixed in 8eac737. Neither finding is a fault a
  simulator would carry; both are the adapter's and the bench tool's.
- The log carried no timestamps, so the first run could not measure the
  interval from the withheld feed to the watchdog reset; the log now stamps
  every line with the tick, the supervisor reports each whole second the
  feed stays withheld, and the third run bounded the interval above.
